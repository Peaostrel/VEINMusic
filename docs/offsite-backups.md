# Зашифрованные бэкапы вне сервера

Локальный `db-backup` продолжает создавать завершённые `.dump`. Дополнительный
сервис restic копирует последнюю завершённую партию в зашифрованный репозиторий S3.
Файлы `.part` не копируются. Сервис запускается отдельно, поэтому отсутствие
внешнего хранилища не ломает основной деплой. **Пока нет реквизитов хранилища,
внешних копий нет.** Этот код не создаёт облачный аккаунт и не включает их сам.

## Настройка владельцем

1. Создать bucket вне этого VPS и отдельные реквизиты с минимальным доступом.
   Настроить versioning/защиту от удаления или Object Lock, если провайдер это
   поддерживает. Ключ, доступный на VPS, не должен позволять уничтожить все
   версии бэкапов; окончательное удаление/retention выполняется отдельными
   реквизитами с доверенного компьютера. Сервис сам не делает forget/prune.
2. В `deploy` скопировать `.env.backup.example` в `.env.backup`, заполнить endpoint,
   bucket, region и AWS-реквизиты провайдера. Сгенерировать уникальный длинный
   пароль restic в `backup-password.txt`. Права на оба файла — `600`.
   Сохранить пароль и ключи шифрования OAuth/TOTP отдельно от VPS: без них
   восстановить данные нельзя. Не отправлять секреты в GitHub или переписку.
3. Инициализировать репозиторий ровно один раз и запустить сервис:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.offsite.yml \
     run --rm --no-deps --entrypoint restic offsite-backup init
   docker compose -f docker-compose.yml -f docker-compose.offsite.yml \
     up -d offsite-backup
   ```

   Сбой сети/пароля не приводит к автоматическому созданию нового репозитория.
   Неудачная загрузка повторяется через минуту; успешная — ежедневно.
   Healthcheck становится unhealthy, если успешной загрузки нет более 30 часов.
   Подключите внешний мониторинг этого статуса: локальный healthcheck сам не
   отправляет уведомления и не доказывает, что сервер ещё доступен.

## Проверка и восстановление

```sh
docker compose -f docker-compose.yml -f docker-compose.offsite.yml \
  run --rm --no-deps --entrypoint restic offsite-backup snapshots
docker compose -f docker-compose.yml -f docker-compose.offsite.yml \
  run --rm --no-deps --entrypoint restic offsite-backup check
```

На отдельном доверенном компьютере с теми же реквизитами и паролем:

```sh
restic restore latest --tag veinmusic-postgres --target ./restore-test
pg_restore --list ./restore-test/backups/<database>-<timestamp>.dump
```

Затем восстановить дамп в **отдельную тестовую PostgreSQL-базу** и проверить
основные сценарии приложения. `pg_restore --list` проверяет структуру файла,
но полноценную проверку восстановления не заменяет. Повторять такую проверку
ежемесячно и после смены схемы/ключей. Не восстанавливать поверх production
до проверки. При возврате старого дампа повторно отозвать сессии и ключи.
