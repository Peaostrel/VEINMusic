# Что делать при подозрении на взлом

Не выполнять этот план в порядке профилактики: он отключает доступ пользователей.
Команды ниже запускает владелец сервера. Никому не отправляйте содержимое `.env`,
дампы и журнал с токенами. Записывайте время действий и признаки инцидента.

1. Ограничить внешний доступ на уровне firewall/Caddy, остановить автодеплой.
   Сохранить копию журналов API, Caddy, SSH и `admin_audit_log` в отдельном месте
   до очистки и восстановления. Не считать содержимое взломанного сервера достоверным.
2. Из каталога `deploy` отозвать все браузерные сеансы, личные API-ключи,
   developer/device-ключи и незавершённые подключения устройств:

   ```sh
   docker compose exec -T backend python -m app.manage revoke-sessions
   docker compose exec -T backend python -m app.manage revoke-sessions \
     --apply --revoke-api-keys --reason 'incident response'
   docker compose restart backend worker
   ```

   Первая команда показывает режим операции без изменений. Вторая атомарно
   увеличивает `session_version` всех пользователей, отзывает ключи/подключения
   и записывает действие в аудит. Без `--revoke-api-keys` отзываются только сеансы.
   Перезапуск API закрывает уже открытые WebSocket, которые нельзя отключить
   одним изменением базы. Новые WebSocket-билеты тоже привязаны к версии сеанса.
   Если сервер скомпрометирован, выполнять отзыв на доверенной копии базы;
   ограничение доступа остаётся до окончания восстановления.
3. С доверенного компьютера сменить пароль базы, Redis, `SECRET_KEY`, секреты
   Spotify/SoundCloud/Last.fm, ключи внешнего хранилища и доступы к SSH/GitHub,
   которые могли быть доступны на сервере. Отозвать OAuth-доступ у провайдеров,
   включая пользовательские токены: замена client secret сама по себе их не отзывает.
   Завершить импорт/фоновые задачи до возвращения сервиса.
4. **Не просто заменить ключ шифрования.** Старые значения OAuth/TOTP иначе
   невозможно расшифровать. Для обычной ротации поддерживаются несколько
   `TOKEN_ENCRYPTION_KEY` (новый первым), но записи надо перешифровать новым
   ключом до удаления старого. При утечке старого ключа не сохранять доступ
   атакующего к новой базе: отключить/отозвать затронутые интеграции и заново
   подключить их; сбросить и перенастроить затронутые TOTP-секреты. Не менять
   `SECRET_KEY` до фиксации отдельного TOKEN_ENCRYPTION_KEY, если шифрование
   ранее зависело от SECRET_KEY. Сохранить ключи для чтения старых бэкапов в
   защищённом архиве вне сервера.
5. Проверить аудит: смену ролей, банов, правил/настроек, выдачу ключей, удаление
   записей. Определить период и объём возможной утечки. Исправить причину на
   чистом сервере, восстановить проверенный бэкап сначала в изолированную БД,
   проверить миграции и приложение. Повторно отозвать сессии/ключи после
   восстановления: старый бэкап может содержать ещё действующие версии.
6. Уведомить затронутых пользователей с проверенными фактами, временем и
   действиями для защиты аккаунта. Вернуть внешний доступ только после
   проверки исправления, новых секретов, 2FA администраторов и внешних бэкапов.

## Двухфакторная защита

Настройки → Безопасность → Двухфакторная защита. Добавьте ключ вручную в приложение
с кодами по времени, подтвердите код и сохраните восемь резервных кодов вне
сервера/телефона. Установка подтверждается паролем, секрет шифруется в БД,
использованный TOTP и резервный код не принимаются повторно. При включении/
отключении все другие сеансы отзываются. API-ключи не получают права на админку.
В production доступ к административным endpoint требует включённой 2FA
(`ADMIN_REQUIRE_2FA=1` в deploy). Вход и настройка остаются доступны для регистрации
фактора; обязательную защиту нельзя отключить через интерфейс.

Если потерян телефон, войдите с резервным кодом. Если потеряны и резервные коды,
восстановление выполняет владелец на доверенном сервере после проверки личности:
отозвать сеансы, очистить TOTP-поля только нужного пользователя, записать операцию
в аудит и заново зарегистрировать фактор. Не отключать обязательную защиту всем.
